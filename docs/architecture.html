① Overview

A small web app that lets multiple browsers control a single Rain Bird ESP-ME3 sprinkler controller — selecting zones, setting run times, building a watering queue, and saving one-tap shortcuts — over a network connection that is genuinely unreliable.

The whole design exists to answer one hard question: how do you build a responsive, multi-client web UI on top of a device that can only hold one connection at a time, frequently refuses connections, and can't be reliably read from?

Many browsers talk freely to the server. Exactly one worker thread talks to the controller.

② The Problem: a Hostile Device

The ESP-ME3's LAN interface (pyrainbird over an encrypted HTTP-on-port-80 protocol) has a set of properties that break the obvious "just call the device when a button is pressed" approach:

PropertyConsequence for naïve designs
One connection at a time Two browsers (or a request + a background poll) hitting the device concurrently → the device resets one. Per-request connections collide constantly.
Intermittent port 80 The device goes unresponsive between internal cycles. A command issued "right now" frequently times out even though the device is fine seconds later.
Unreliable reads get_current_irrigation() / get_rain_sensor_state() often time out. You cannot trust the device to tell you what it's doing.
Whole-minute, single-zone No "add 30 seconds", no concurrent zones, no stored programs over the local API. Anything richer must be built on top.
⛔ The trap we escaped
The original design opened a fresh connection per HTTP request and read state back from the controller. Result: stop/adjust commands hung for the device's full timeout, the connection status flapped every few seconds, and a wrong/offline IP froze the whole UI at 0:00.
💡 The reframe
Treat the controller as a write-mostly actuator, not a database. The server remembers what should be happening; a single worker nudges the device toward that goal and retries patiently when the device isn't listening.

③ Design Principles

🗄️ Server owns truth

The watering queue lives on the server. The device is never the source of truth — we don't read state back from it.

🧵 One writer

A single background worker owns the one allowed connection. No other code path ever calls the controller.

🎯 Level-triggered

The worker compares desired vs applied and computes the next command. It's not event-driven, so a missed event can't desync it.

⏳ Patient retries

Failures schedule an exponentially-backed-off retry with jitter, capped at 30s. Never hammer a busy device.

⏱️ Honest timers

A zone's countdown starts only after its start command is confirmed. The timer reflects reality.

🔄 Everyone in sync

Every change bumps a version and wakes long-pollers, so all browsers converge within ~1 second.

④ Components

Handlers mutate state under the lock; the worker reads state and drives the device. The lock is the only shared-memory contract.

⑤ State Model

The heart of the system is two pieces of state and the relationship between them:

Desired — queue[]

An ordered list of jobs. The head is what should be watering. Clients freely add, remove, reorder, and edit jobs. Each job:

{
  "id": "a1b2c3d4",      // stable handle
  "zone_id": 2,
  "duration_sec": 900,
  "ends_at": null        // set ONLY when confirmed running
}

Applied — applied

What the worker has confirmed the controller is doing:

  • None → device is stopped (or we believe so)
  • (job_id, zone) → device was told to water this job

The worker's entire job is to make applied match the head of queue. When they differ, it issues exactly one command.

Head job lifecycle

A head sits in starting — with no countdown — until the device confirms the command. Only then does it become running.

⑥ The Worker Loop

One thread, one asyncio event loop, one connection. Every tick it runs the same level-triggered logic:

while True:
    expire_finished_head()        # 1. countdown hit 0? pop & advance
    ensure_session()              # 2. (re)connect if IP/pw changed

    if now < next_attempt:          # 3. in backoff cooldown?
        sleep_until_work(...)     #    wait it out (wake early on edits)
        continue

    reconcile_once()              # 4. ONE command toward the goal

    if idle and due:               # 5. best-effort rain-sensor read
        poll_rain_sensor()

    sleep_until_work(1.0)         # wake instantly on any change

reconcile_once() — the decision table

Head of queueappliedAction
— (empty)NoneNothing. Controller idle. idle
— (empty)(j,z)stop_irrigation() → applied=None
job J / zone Z(J,Z)Already correct. Nothing. watering
job J / zone ZNone or otherstop (if needed), then irrigate_zone(Z, mins). On success: set ends_at, applied=(J,Z)
💡 Why level-triggered?
The worker never relies on "an event happened." It only ever asks "does reality match the goal?" If a client makes three rapid edits, or an event is missed, or the worker restarts — it doesn't matter. The next tick re-derives the one correct command from current state. This is the same principle Kubernetes controllers use, and it's why the system is hard to desync.

⑦ Retry & Exponential Backoff

When a command fails (timeout, connection reset, device busy), we don't retry immediately — that just adds load to a device that's already struggling. Instead we schedule the next attempt with capped exponential backoff plus jitter:

delay = min(30s, 1s × 2n) × (1 ± 0.3 jitter)
# n grows on each consecutive failure, resets to 0 on success
Retry spacing grows 1→2→4→8→16→30s (jittered), then holds at the 30s cap until the device answers — then resets to zero.

The same backoff covers both failure types you asked about:

  • Command rejected/timed out — the device was reachable but busy/unresponsive.
  • Connection failed — couldn't even open the socket (wrong IP, device asleep).

While retrying, the UI shows Retrying in Ns with a live countdown to the next attempt, so it's obvious the system is working the problem, not stuck.

⚠ Reads are exempt
The best-effort rain-sensor poll does not trigger backoff or flip the device offline on failure — reads from the ESP-ME3 are inherently unreliable and we don't want a failed read to look like a real fault. Only commands drive the backoff/online machinery.

⑧ Queue Timing & Scheduling

The queue runs jobs sequentially, head-first, entirely server-side (the ESP-ME3 has no concept of a queue). The flow:

  1. The head's start command is confirmed → its ends_at = now + duration is set. The countdown is now authoritative and ticks independently of the device.
  2. When now ≥ ends_at, the worker pops the head and advances. applied is cleared so the next head gets started.
  3. The next head is a fresh target → the worker issues its start command, and the cycle repeats.

Editing the queue mid-run

Any change is just a state mutation under the lock, followed by a version bump that wakes the worker. The worker re-derives the correct command:

Client actionEffect on headWorker response
Add (queue empty)new headstart it
Add (already running)appended, stays pendingnothing until it reaches head
Run-now / shortcutinserted at headstop current, start new head
Reorder a new job to tophead changesapplied≠head → re-apply
Edit duration of headends_at cleared, retargetre-apply with new minutes
±5/±15 adjustremaining time changed, retargetstop + restart at new time

⚠ Why adjust = stop + restart
The ESP-ME3 has no "add 5 minutes" command. To change a running zone's time we must stop it and re-issue irrigate_zone with the new total. The worker handles this transparently via the retarget → re-apply path; the user just sees the timer jump.

⑨ Multi-Client Sync

Every browser stays live without polling spam, using long-polling on a version number:

B parks on ?since=41. When A's change bumps the version to 42, the server wakes B's request immediately — B re-renders and re-parks. No polling loop, sub-second convergence.

The same mechanism delivers worker-driven changes (a job confirmed running, a retry scheduled, the countdown advancing the queue) to every browser — the worker bumps the version exactly like a client edit does.

💡 The net effect
The UI is always responsive and always honest. Editing the queue never blocks on the device. A flaky controller shows as "retrying," not "broken." And whatever you see in one browser, everyone sees within a second.
